# 체계적 분석 프레임워크 v2

검토일: 2026-11-08

이 문서는 tldraw, H5P, Twine, Artsteps, Excalidraw를 같은 잣대로 비교하기 위한 분석 규격이다. 기능 목록 비교를 피하고, 실제 제품 구조와 놀 서비스 적용 가능성을 판단하는 것이 목적이다.

## 1. 증거 등급

| 등급 | 의미 | 허용되는 표현 |
|---|---|---|
| A1 | 공식 소스 코드에서 직접 확인 | "~로 구현되어 있다" |
| A2 | 공식 기술 문서/규격에서 직접 확인 | "~를 지원/정의한다" |
| B | 공식 서비스/공식 제품 설명에서 관찰 | "~로 안내/노출된다" |
| C | A/B에 기반한 구조적 추론 | "~로 해석할 수 있다" |
| D | 놀 서비스 적용 제안 | "~를 도입하는 것이 좋다" |

C/D를 A처럼 단정하지 않는다. 비공개 서비스인 Artsteps는 A1 수준 검증이 불가능하므로 특히 엄격하게 구분한다.

## 2. 10개 공통 분석 축

### ① User Job
사용자가 제품을 열어서 완료하려는 핵심 과제는 무엇인가?
- 시작 상태
- 핵심 행동
- 완료 상태
- 반복 사용 시 달라지는 점

### ② Information Architecture
기능이 어떻게 묶이는가?
- 항상 노출
- 선택/맥락별 노출
- 고급 기능
- 제작/실행/관리 영역 분리

### ③ Domain / Data Model
결과물의 최소 단위는 무엇인가?
- record, content type, passage, artifact 등
- ID 안정성
- 참조 관계
- 자산과 메타데이터 관계

### ④ Ephemeral / Persistent State
무엇을 기억해야 하고 무엇은 버려도 되는가?
- 콘텐츠
- 편집기 세션
- 재생/관람 세션
- 협업 presence
- UI preference

### ⑤ Persistence / Recovery / Sync
- localStorage / IndexedDB / 파일 / 서버
- autosave 방식
- schema migration
- 멀티탭
- 자산 blob
- quota 및 저장 실패
- 실시간 협업

### ⑥ Extensibility
새 기능을 어떻게 추가하는가?
- plugin/type/manifest
- schema
- dependency
- author/runtime contract
- versioning

### ⑦ Error & Integrity Model
제품이 어떤 잘못된 상태를 검출하는가?
- 끊어진 참조
- 호환되지 않는 버전
- 누락 자산
- 순환/도달성
- 저장 실패
- 충돌

### ⑧ Accessibility / Device Model
- 키보드
- 터치
- 화면 크기
- reduced motion
- 3D 대체 경로
- 학교 저사양 기기

### ⑨ Operational / Legal Risk
- 라이선스
- 외부 서버 의존
- 개인정보
- 번들/성능
- 유지보수성

### ⑩ Knol Transfer
각 패턴을 다음 중 하나로 판정한다.
- **ADOPT**: 원리를 바로 적용
- **ADAPT**: 현재 구조에 맞게 변형
- **DEFER**: 선행 조건 후 검토
- **REJECT**: 비용/위험이 이득보다 큼
- **ALREADY**: 현재 놀 서비스에 이미 더 적합한 구현이 있음

## 3. 평가는 점수가 아니라 의사결정으로

1~5 숫자 합산은 정밀해 보이지만 근거가 약할 수 있다. 이 저장소는 우선 ordinal 판단을 사용한다.

- 가치: 매우 높음 / 높음 / 중간 / 낮음
- 적용 비용: 낮음 / 중간 / 높음
- 위험: 낮음 / 중간 / 높음
- 증거 강도: A1/A2/B/C/D

숫자 ROI는 실제 개발 시간·사용성 실측 후에만 계산한다.

## 4. 적용 우선순위 공식

우선순위는 다음 순서로 결정한다.

1. 현재 실제 문제가 존재하는가
2. 외부 패턴이 그 문제를 직접 해결하는가
3. 현재 코드 구조와 충돌하지 않는가
4. 데이터 마이그레이션 위험이 낮은가
5. 교실 환경에서 체감 효과가 있는가
6. 작은 실험으로 검증 가능한가

## 5. 분석 완료의 Definition of Done

한 도구의 분석은 다음이 모두 있어야 완료로 본다.
- 공식 근거 2개 이상
- 가능한 경우 실제 소스 파일 1개 이상
- 데이터/상태 모델
- 저장·복구 실패 모드
- 라이선스 확인
- 우리 저장소 현재 구현과 대조
- 적용/보류/거절 판단
- 최소 실험과 통과 기준
- 확인하지 못한 항목 기록

## 6. 금지 사항

- "유명해서 좋다" 같은 인기도 기반 결론
- UI 모양만 복제
- source-available을 permissive open source로 오해
- hosted app 기능을 SDK 기능으로 오해
- 기능 이름이 같다는 이유로 내부 구조도 같다고 가정
- 현재 놀 서비스에 이미 있는 구조를 다시 만들기
- 외부 패턴 때문에 기존 데이터 호환성을 깨기
