# 02. H5P 분석

## 한 줄 결론

H5P에서 가장 참고할 것은 개별 퀴즈 기능이 아니라 **교육 활동을 독립적인 콘텐츠 타입으로 정의하고, 공통 런타임·에디터·패키지 형식 위에서 재사용하는 구조**입니다.

## 왜 분석하는가

놀퀴즈 계열 서비스가 계속 늘어날수록 ‘새 기능 하나 = 새 웹페이지 하나’ 방식은 유지보수 비용이 빠르게 커집니다. H5P는 Multiple Choice, Interactive Video, Branching Scenario, Virtual Tour 같은 서로 다른 활동을 하나의 생태계 안에서 확장합니다.

## 확인된 사실

### A. 콘텐츠 타입이 핵심 단위

H5P는 Interactive Video, Course Presentation, Branching Scenario, Quiz, Image Hotspots, Virtual Tour 등 다양한 활동 유형을 제공합니다.

사용자는 ‘빈 편집기’에서 모든 것을 만드는 것이 아니라 **하고 싶은 활동 유형을 먼저 고른 뒤 그 타입에 맞는 편집기**를 사용합니다.

### B. 라이브러리 기반 모듈 구조

H5P의 building block은 library입니다. library는 content type, editor widget, API helper가 될 수 있고 다른 library에 의존할 수 있습니다.

따라서 신규 활동은 전체 플랫폼 코드를 뜯어고치기보다 새로운 library를 추가하는 방식으로 확장할 수 있습니다.

### C. semantics.json이 데이터와 편집 UI를 연결

`semantics.json`은 해당 콘텐츠 타입이 어떤 입력값을 받는지 정의합니다. H5P editor는 이 정의를 읽어 기본 입력 폼을 생성하고, 런타임에서는 콘텐츠 데이터의 유효성 검사에도 사용합니다.

이 방식의 핵심은 **콘텐츠 스키마가 곧 편집기의 계약(contract)** 이 된다는 점입니다.

### D. .h5p는 이식 가능한 패키지

`.h5p`는 특정 구조를 가진 ZIP 기반 패키지이며 `h5p.json`, `content/content.json`, 필요한 library와 media를 포함할 수 있습니다.

사용자는 Reuse → Download로 콘텐츠를 내려받고 다른 H5P 지원 사이트에 Upload할 수 있습니다.

### E. 부분 재사용도 고려

같은 H5P 환경 안에서는 특정 질문이나 하위 콘텐츠를 복사해 다른 콘텐츠에 붙여넣을 수 있습니다. 즉 재사용 단위가 전체 파일에만 한정되지 않습니다.

### F. Branching Scenario는 복합 타입

Branching Scenario는 텍스트, 이미지, Course Presentation, Interactive Video 등 다른 H5P 타입을 노드 안에 넣을 수 있습니다. 선택에 따라 다른 노드로 이동하며 결말별 점수나 피드백을 줄 수 있습니다.

이것은 ‘활동 타입끼리 조합 가능하게 설계하는 것’의 대표 사례입니다.

## 핵심 설계 모델

```text
Platform
 ├─ Core runtime
 ├─ Editor
 ├─ Content type registry
 │   ├─ Multiple Choice
 │   ├─ Drag & Drop
 │   ├─ Interactive Video
 │   ├─ Branching Scenario
 │   └─ ...
 └─ Package / import / export

Content Type
 ├─ schema / semantics
 ├─ authoring UI
 ├─ runtime behavior
 ├─ dependencies
 └─ assets
```

## UX에서 가져올 패턴

### 1. ‘무엇을 만들지’부터 선택

초보 사용자에게 범용 편집기를 먼저 보여주기보다 다음처럼 시작합니다.

- 퀴즈 만들기
- 이미지에서 찾기
- 순서 맞추기
- 선택에 따라 달라지는 이야기
- 작품 감상 활동
- 360/3D 공간 탐색

활동 목적이 UI 구조를 결정하게 하는 방식입니다.

### 2. 콘텐츠 타입마다 필요한 옵션만

Multiple Choice 사용자가 3D 옵션을 볼 이유가 없습니다. 유형별 편집 UI를 분리하면 초보자 화면이 단순해집니다.

### 3. 재사용을 기본 동작으로

‘복제’ 기능보다 더 나아가, 내 활동함에서 질문 하나·활동 블록 하나를 꺼내 재사용할 수 있게 만들 수 있습니다.

### 4. 데이터 포맷을 서비스보다 오래 살게 하기

서비스 UI가 바뀌어도 콘텐츠 JSON 스키마와 migration만 유지하면 과거 자료를 계속 불러올 수 있습니다.

## 우리 서비스 적용안

### 놀퀴즈

가장 직접적인 적용 후보입니다.

현재/향후 활동을 다음처럼 type registry로 관리하는 방식을 검토할 수 있습니다.

```text
multiple-choice
true-false
short-answer
matching
ordering
image-hotspot
drag-drop
branching
timeline
reflection
```

각 타입은 공통 인터페이스를 가집니다.

```text
id
version
title
schema
defaultData
validate(data)
renderAuthor(data)
renderPlayer(data)
export(data)
migrate(oldData)
```

### 놀스토리 / 놀히스토리

H5P Branching Scenario 자체를 따라가기보다는 ‘다른 콘텐츠 타입을 노드 안에 넣을 수 있다’는 아이디어를 참고할 가치가 큽니다.

예를 들어 역사 사건 노드에:

- 선택지
- 사료 이미지
- 짧은 퀴즈
- 지도
- 결과 피드백

를 조합할 수 있습니다.

### 신규 서비스 발굴

H5P의 타입 목록은 신규 웹도구 후보를 발굴하는 카탈로그로도 쓸 수 있습니다.

우선 검토 가치가 높은 유형:

- Image Hotspots
- Timeline
- Interactive Book
- Virtual Tour
- Sort the Paragraphs
- Memory Game
- Dictation
- Branching Scenario

단, ‘H5P에 있으니 만든다’가 아니라 초등 교육과정의 실제 수업 흐름과 연결되는지 먼저 판단해야 합니다.

## 그대로 가져오면 안 되는 점

### 1. 타입 수가 많을수록 선택 피로가 생김

H5P의 강점인 많은 유형은 동시에 약점이 될 수 있습니다. 초등 교사에게 40~50개 타입을 그대로 보여주기보다 ‘수업 목적’ 기준으로 5~8개 범주에 묶는 편이 낫습니다.

### 2. 범용 schema editor는 딱딱해질 수 있음

`semantics.json`처럼 schema 기반으로 폼을 자동 생성하더라도, 학생/교사용 핵심 활동은 전용 UX를 추가해야 합니다.

### 3. LMS 중심 구조를 그대로 복제할 필요 없음

우리 서비스는 설치형 LMS가 아니라 빠르게 접속하는 웹도구가 많습니다. H5P의 플랫폼 통합 구조보다 콘텐츠 타입·패키징·재사용 개념만 추출하는 것이 적합합니다.

## 구현 실험

### 실험 H1 — activity registry

놀퀴즈 내부의 기존 활동 2~3개를 공통 registry 인터페이스로 래핑합니다.

검증:

- 새 타입 추가 시 기존 라우터/저장 로직 변경이 최소화되는가
- 공통 export/import가 가능한가
- 타입별 버전 migration이 가능한가

### 실험 H2 — 자체 `.knolactivity` 패키지

장기적으로는 ZIP까지 갈 필요 없이 초기 버전은 JSON으로 시작할 수 있습니다.

```json
{
  "format": "knol-activity",
  "version": 1,
  "type": "ordering",
  "data": {},
  "meta": {}
}
```

필요해지면 media assets를 포함한 ZIP 패키지로 확장합니다.

### 실험 H3 — 내 활동함 블록 재사용

전체 활동 복제뿐 아니라 ‘문항 1개’, ‘이미지+질문 블록’ 단위 재사용을 실험합니다.

## 판단

- **원리 채택:** 매우 높음
- **구조 참고:** 매우 높음
- **H5P 자체 통합:** 현재는 낮음. 우리 UX·배포 방식과 맞는 부분만 자체 구조로 흡수하는 편이 유리
