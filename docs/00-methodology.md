# 분석 방법론

## 목적

이 저장소의 목표는 외부 서비스를 평가표처럼 점수화하는 것이 아니라, **실제로 구현 가능한 설계 지식**으로 변환하는 것입니다.

## Craft Anything에서 가져온 관점

`storytold/craft-anything`은 소프트웨어를 Study → Build → Check → Ready 흐름으로 다룹니다. 이 저장소에서는 직접 재구축이 목적이 아니므로 다음처럼 변형합니다.

### 1. Study — 실제로 무엇이 보이고 어떻게 동작하는가

- 첫 진입 흐름
- 핵심 작업의 최소 클릭 수
- 편집 중 상태 변화
- 저장·복구·공유
- 오류나 빈 상태
- 모바일/태블릿에서의 조작 가능성

### 2. Evidence — 무엇을 근거로 말하는가

근거는 세 층으로 기록합니다.

- **A: 공식 문서/공식 코드에서 직접 확인**
- **B: 공식 서비스의 실제 UI나 동작에서 관찰**
- **C: A/B를 바탕으로 한 설계 추론**

C는 사실처럼 쓰지 않고 반드시 ‘추론’ 또는 ‘적용 제안’으로 표시합니다.

### 3. Model — 내부 구조를 어떤 모델로 이해할 수 있는가

다음 질문에 답합니다.

- 핵심 데이터 단위는 무엇인가?
- 편집 상태와 결과물 상태가 분리되는가?
- 저장은 전체 스냅샷인가, 변경 이벤트인가?
- 콘텐츠 타입/플러그인/노드 확장이 가능한가?
- 제작기와 실행기가 분리되는가?
- 공유 단위는 파일, 링크, 방(room), 패키지 중 무엇인가?

### 4. Transfer — 놀퀴즈 계열 서비스에 무엇을 가져올 것인가

각 아이디어를 다음 3단계로 분류합니다.

- **원리 채택**: 제품과 무관하게 바로 적용할 설계 원리
- **구조 참고**: 데이터 모델·상태관리·콘텐츠 구조를 참고
- **직접 도입 검토**: 오픈소스 패키지/SDK를 실제 의존성으로 쓸지 검토

### 5. Check — 적용 전에 무엇을 검증해야 하는가

- 초등학생이 설명 없이 사용할 수 있는가
- 태블릿 터치로 동일하게 작동하는가
- 새로고침/탭 종료 후 복구되는가
- 오프라인 또는 불안정 네트워크에서 치명적 손실이 없는가
- 공유 링크가 개인정보를 노출하지 않는가
- 저장 포맷 마이그레이션이 가능한가
- 외부 SDK/코드의 라이선스가 실제 배포 조건에 맞는가

## 문서 템플릿

각 서비스 분석 문서는 다음 순서를 기본으로 합니다.

1. 한 줄 결론
2. 왜 분석하는가
3. 확인된 사실
4. 핵심 설계 모델
5. UX 패턴
6. 우리 서비스 적용안
7. 그대로 가져오면 안 되는 점
8. 구현 실험
9. 근거 링크

## 라이선스 원칙

‘오픈소스처럼 보인다’와 ‘우리 서비스에 그대로 넣어도 된다’는 같은 말이 아닙니다. 예를 들어 tldraw SDK는 2026년 현재 기본 라이선스상 개발 환경 사용과 프로덕션 사용 조건이 다릅니다. 따라서 이 저장소는 **패턴 분석**과 **코드 재사용 판단**을 분리합니다.
